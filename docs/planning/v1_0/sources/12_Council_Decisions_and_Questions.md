## 2. Original assumptions affected

The Android proposal is confirmed as a platform choice; the Kotlin/Compose and C++/Oboe implementation remains a recommendation to verify. Interface and splitter allowance is confirmed, but no exact device/accessory combination has been certified. The previous assumption that video, karaoke, broadcast and plugin hosting could remain open is replaced by selected scope. Their delivery may be staged internally, but agents cannot call a reduced beta the finished product.

The source premise has become more demanding: broad catalogs matter to the user, particularly the secondary audience. Phone-native local delivery remains the selected first architecture. It must still preserve broad source ambition and requested in-app link acquisition; local first does not narrow the final source scope to manually imported files only. At the same time, required permissions and usable APIs are external dependencies. Track unavailable adapters honestly and raise a specific acceptance decision if concrete feasibility evidence leaves a selected source requirement unmet. A broad unanswered provider questionnaire does not block design.

The visual decision is **C — Crystal Current**. Develop pale optical glass, titanium, restrained brass and dark-ink labels on the Galaxy S26 Ultra. Low-light and accessibility treatments should derive from C; the owner did not choose the proposed A/night+C/day combination. Its exact native layout, contrast and performance remain unverified.

The owner selected ParDay preparation plus armed assisted performance. Unarmed live behavior remains read/propose, and each bounded audible plan is explicitly armed. ParDay introduces language-model data egress, cost, stale actions and prompt injection. It also creates an opportunity to make a large professional tool quicker to use. Stem separation and beat analysis remain distinct DSP/ML functions; naming an assistant does not merge these workloads into a conversational model.

## 4. Scenarios that change the plan

| Scenario | Required response | Decision effect |
| --- | --- | --- |
| A requested provider restricts an operation | Keep technical function, provider access, content rights and distribution review separate; show the specific affected operation | Research an alternate acquisition route on its own evidence; it does not inherit clearance merely because it returns a file |
| AI responds after the DJ replaces a deck | Reject stale generation/revision or expiry; offer a fresh proposal | Never execute on the replacement track |
| Phone is hot with live stems, video and broadcast | Shed optional conversation/preparation/render decoration first; test the exact active workload | If protected sound cannot be sustained, that combination is uncertified |
| Plugin crashes or misses its bounded budget | Follow tested bypass/isolation policy; report failure without corrupting the session | Unsafe host/format cannot ship as supported |
| Assistant suggests the wrong recording or downbeat | Expose confidence, exact edition and preview; preserve manual correction | Utility depends on measured metadata and user review, not fluent explanation |
| Source is cleared for local use but not broadcasting | Disable broadcast for that mix/source under its capability rule | Private practice is not treated as broadcast permission |
| ParDay API is offline or quota exhausted | Preserve all local DJ controls and valid saved preparation | Cloud assistant cannot become an audio dependency |

The strongest pre-mortem is a visually impressive app that cannot admit the desired catalogs, overloads common phones and requires too many confirmations to be quick. The opportunity case is a reliable instrument whose assistant turns a large eligible local library into a prepared, understandable set faster than competing workflows. Both outcomes depend on evidence outside these renders.

## 5. Chair synthesis and surviving objections

Maintain the native local-engine direction with selected C, Galaxy S26 Ultra first-device validation, ParDay armed assistance, the requested link-acquisition module and the selected specialist modules. Evaluate unofficial extraction candidates rather than treating official API access as a universal technical prerequisite. Keep source eligibility and user authority enforced beneath the UI. Proceed with a replaceable model adapter rather than binding the app identity to one provider. Prefer compatible open source for DSP where it meets the actual quality and maintenance requirements, while retaining a measured paid comparison.

**Strongest argument against this direction:** the combined scope may exceed the available budget/team and the mobile hardware or partner ecosystem may not support every desired combination. Planning completeness cannot solve missing provider agreements or unsupported plugin formats. Before promising a release date, run G1 and obtain the actual resource constraints.

**Historical minority report, updated:** personal deployment and local-first implementation are selected. The earlier suggestion of a tightly reduced feature set is not. Preserve the complete professional scope and requested link acquisition on the phone, with future AWS expansion evaluated separately. Bring-your-own AI credentials and an optional gateway remain implementation options; a smaller milestone still does not complete the product.

The design choice is reversible. Vendor coupling, plugin ecosystem, source agreements, data retention and release promises are more costly to reverse. Validate those earlier than exhaustive screen polish.
